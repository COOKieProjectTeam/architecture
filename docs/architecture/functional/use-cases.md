# Функциональная архитектура — варианты использования

_Текстовые актёры, граница системы и сценарии **Use Case** без PlantUML; детали требований — в [[../../requirements/SRS|SRS]]. Продуктовый контекст: [[../../product/overview|Обзор продукта]]._

## Актёры

### Роли приложения (согласованы с SRS §2.2)

| Роль                  | Назначение в сценариях                                                                                                     |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **Anonymous User**    | Воронка без регистрации; ограничения по конфигурации продукта                                                              |
| **Free User**         | Поиск, рецепты, КБЖУ, базовые функции; ограничения подписочных фич                                                         |
| **Pro User**          | Подписка **Pro**: планирование питания, список покупок и **hand-off** к партнёрам; ИИ-помощник — вторичный модуль ценности |
| **Content Moderator** | Модерация рецептов и UGC, статусы публикации                                                                               |
| **Admin**             | Администрирование платформы (полный доступ в границах системы)                                                             |
| **Partner Manager**   | B2B: каталог готовой еды партнёра, аналитика заказов                                                                       |

### Внешние (secondary actors)

| Актор | Роль |
|-------|------|
| **Retailer partner** | Ритейлер; каталог SKU, приём переданной корзины / hand-off по контракту |
| **Food delivery partner** | Сервис доставки еды; те же классы операций интеграции |
| **LLM provider** | Внешние API для чат-диетолога и рекомендаций (**OpenAI** / **Anthropic** по SRS) |
| **Payment gateway** | Платежи и подписки (например **ЮKassa**), см. дорожную карту SRS |
| **External recipe sources** | Сайты/видео для **парсинга** рецептов (ограниченный список MVP в SRS) |

_Конкретные URL партнёрских API и финальный перечень провайдеров не фиксируются здесь — см. SRS §7. Роли приложения согласованы с SRS §2.2 (сверка 2026-05-03); на доске `summary/` возможны сокращения имён актёров — см. примечание в [[../../meta/stakeholders|Стейкхолдеры]]._

## Граница системы (UML step A — scope)

**Внутри COOKie (платформа):** учёт пользователей и подписок; каталог и жизненный цикл рецептов; парсинг и обогащение данных; расчёт и отображение КБЖУ; планирование питания и списки покупок; сбор аналитики событий; интеграционные **точки** для передачи корзины / заказа партнёрам; ИИ-функции как обёртка над внешними моделями; модерация и администрирование.

**Снаружи:** оплата и финализация заказа у партнёра (часто в их приложении/вебе); отслеживание статуса заказа и доставки **в приложениях партнёров** после hand-off; первичные источники рецептов в интернете; инфраструктура и SLA партнёрских API.

Сводный продуктовый смысл границы — [[../../product/overview|обзор продукта]]; формальный scope — [[../../requirements/SRS|SRS]] §1.2.

## Варианты использования (текст, UML step B)

Имена префикса **`UC-`** на английском; описание на русском. Связь с SRS — ориентиры по группам FR, без перечисления всех под-пунктов.

### UC-BrowseRecipes

- **Цель:** найти рецепты по запросу и фильтрам.
- **Акторы:** Anonymous User, Free User, Pro User.
- **Связь:** FR-RS-002.
- **Main flow:** ввод условий поиска → применение фильтров → просмотр страницы результатов → переход к карточке.

### UC-ViewRecipe

- **Цель:** открыть карточку рецепта с вкладками (обзор, ингредиенты, шаги, КБЖУ, история) и действиями (избранное, рейтинг, шэр — по роли и фичефлагу).
- **Акторы:** Anonymous User, Free User, Pro User.
- **Связь:** FR-RS-003, FR-DE-002 (согласованность расчёта КБЖУ).
- **Main flow:** выбор рецепта из поиска/похожих → загрузка карточки → просмотр вкладок / масштаб порций → при необходимости событие `recipe_view` (FR-AN-001).

### UC-Authenticate

- **Цель:** регистрация, вход, восстановление доступа по политике продукта.
- **Акторы:** Anonymous User → Free User / Pro User.
- **Связь:** FR-US-001.
- **Main flow:** выбор метода входа → проверка учётных данных / OAuth-поток (см. SRS) → установка сессии.

### UC-ManageUserProfile

- **Цель:** задать предпочтения, диету, аллергены и параметры для персонализации и планирования.
- **Акторы:** Free User, Pro User.
- **Связь:** FR-US-002; влияние на FR-RS-002.5 (персонализация выдачи), FR-MP-001.

### UC-ManageFavorites

- **Цель:** вести ограниченный объём избранного для Free и расширенный/полный для Pro по правилам SRS.
- **Акторы:** Free User, Pro User.
- **Связь:** FR-US-003.

### UC-RateRecipe

- **Цель:** выставить или изменить оценку рецепта по шкале **1–5** (одна активная оценка на рецепт на пользователя).
- **Акторы:** Free User, Pro User.
- **Связь:** FR-RS-004.

### UC-GenerateMealPlan

- **Цель:** сгенерировать план питания на период (день…месяц) с целевыми КБЖУ и ограничениями.
- **Акторы:** Pro User.
- **Связь:** FR-MP-001.
- **Main flow:** задать горизонт и приёмы пищи → система подбирает рецепты → пользователь правит слоты → просмотр календаря и сводки КБЖУ.

### UC-BuildShoppingList

- **Цель:** собрать агрегированный список покупок из плана и/или рецепта, оценить стоимость, отмечать купленное.
- **Акторы:** Pro User (ядро ценности Pro вместе с интеграциями).
- **Связь:** FR-MP-002 (в т.ч. FR-MP-002.4 — передача корзины партнёру).

### UC-PartnerHandOff

- **Цель:** инициировать **hand-off** состава корзины или списка к выбранному **Retailer partner** или **Food delivery partner** и продолжить сценарий заказа в **приложении партнёра** (оплата, статус, доставка).
- **Акторы:** Pro User; secondary: Retailer partner, Food delivery partner.
- **Связь:** FR-MP-002.4, FR-OR-001.3, INT-API-006.

### UC-BrowseOrderReadyMeals

- **Цель:** работать с **отдельным** каталогом готовых блюд партнёра (не маппить обязательно на рецепты COOKie), сформировать корзину и передать её партнёрскому каналу.
- **Акторы:** Free User / Pro User (по дорожной карте фазы); Partner Manager задаёт содержание каталога.
- **Связь:** FR-OR-001.

### UC-ChatNutritionAI

- **Цель:** получить ответы чат-консультанта и персонализированные рекомендации по питанию.
- **Акторы:** Pro User.
- **Акторы (внешние):** LLM provider.
- **Связь:** FR-AI-001, FR-AI-002; модерация опасных запросов — см. SRS.

### UC-IngestRecipes

- **Цель:** наполнять и обновлять корпус рецептов из **External recipe sources** с дедупликацией и валидацией.
- **Акторы:** инициируется **платформой** (планировщик); Content Moderator участвует в разборе дубликатов/спорных случаев.
- **Связь:** FR-PS-001, FR-PS-002; FR-RS-001 (статусы, источник).

### UC-ModerateRecipes

- **Цель:** переводить рецепты по статусам модерации, управлять UGC в рамках политики.
- **Акторы:** Content Moderator.
- **Связь:** FR-RS-001 (модерация, `source_type` в т.ч. `ugc`).

### UC-PartnerAnalytics

- **Цель:** просматривать аналитику по каталогу готовой еды и конверсиям для B2B-партнёра.
- **Акторы:** Partner Manager.
- **Связь:** FR-OR-001.4, FR-AN-002/003 (в части отчётности — уточняется в SRS).

### UC-AdministerPlatform

- **Цель:** операции администрирования, не выделенные отдельным UC (конфигурация, доступы, согласованные с SRS сценарии).
- **Акторы:** Admin.
- **Связь:** роль Admin в SRS §2.2; конкретные FR — по мере детализации в спеках.

### UC-ManageProSubscription

Дополнение к дорожной карте оплат (SRS: **ЮKassa**, Phase 2+ для полного платёжного контура MVP).

- **Цель:** оформить, продлить или отказаться от платного тарифа **Pro**; получить подтверждение успешной оплаты и актуальный статус подписки в профиле.
- **Акторы:** Free User / Pro User; secondary: **Payment gateway** (**ЮKassa**).
- **Связь:** `INT-API-002`, события `subscription_*` в `FR-AN-001`, ценность Pro в SRS §2.2 и блоке перед FR-AI.

**Диаграмма (UML, смысл):** слева **User** → в границу системы **«Оформить Pro»**, **«Проверить статус подписки»**, **«Отменить автопродление»** (набор можно слить в один UC «Управление подпиской Pro» на схеме); справа за границей — **Payment gateway**; пунктирная ассоциация от **«Оформить Pro»** к **Payment gateway** (внешний платёж).

**Main flow (оформление):** открыть экран тарифов → выбрать Pro → переход на оплату у провайдера → webhook/callback успеха → активация Pro в учётке → пользователь получает подтверждение UI.

**Альтернативы:** отказ на шаге оплаты (статус Free сохранён); ошибка платежа (сообщение, повтор попытки); просроченный платёж при продлении (политика grace — по продукту, фиксируется в SRS/NFR при детализации).

### UC-ManagePersonalData

- **Цель:** выполнить требования к персональным данным: согласие, экспорт «пакета данных» пользователя, удаление аккаунта (**right to erasure**) с санитизацией UGC по правилам SRS.
- **Акторы:** Free User, Pro User (и бывшие пользователи на шагах после подачи запроса — по процессу).
- **Связь:** `DR-GDPR-001`…`DR-GDPR-004`, пересечение с регистрацией `FR-US-001`.

**Диаграмма (UML, смысл):** **User** → внутри системы **«Дать / отозвать согласие»**, **«Экспортировать мои данные (JSON)»**, **«Удалить аккаунт»**; опционально участвует **Email provider** как secondary только если экспорт отправляется письмом (если предусмотрите — иначе не показывать на схеме).

**Main flow (экспорт):** настройки приватности → запрос экспорта → формирование архива / JSON → скачивание или отправка по политике.

**Main flow (удаление):** явное подтверждение (двухшаговое) → отзыв токенов → удаление PII → анонимизация созданного контента по `DR-GDPR-002` → подтверждение пользователю.

### UC-RestoreAccountAccess

Развертка входа (**include** относительно **UC-Authenticate**), чтобы трассировать приёмочные тесты и почтовые потоки.

- **Цель:** подтвердить адрес почты после регистрации и восстановить пароль без компрометации учётки.
- **Акторы:** Anonymous User или пользователь без активной сессии; secondary: канал email (transactional из SRS §7).
- **Связь:** `FR-US-001.3`, `FR-US-001.5`, `INT-API-003` (email-провайдер).

**Диаграмма (UML, смысл):** **User** ↔ **«Подтвердить email по ссылке»**; **User** ↔ **«Сбросить пароль по токену»**; пунктир от обоих к **Email service** за границей.

**Main flow (подтверждение email):** регистрация → письмо со ссылкой → переход по токену → флаг verified в профиле.

**Main flow (сброс пароля):** запрос сброса → письмо с ограниченным по времени токеном → форма нового пароля → инвалидация старых сессий по политике безопасности.

### UC-OperateProductReporting

- **Цель:** просматривать продуктовую и техническую аналитику (дашборды, отчёты по календарю, выгрузки), необходимые для решений по релизам и качеству.
- **Акторы:** Admin (или выделенная роль продукта, если позже выделите из Admin — до тех пор **Admin**).
- **Связь:** `FR-AN-002`, `FR-AN-003`, при необходимости части Observability из NFR.

**Диаграмма (UML, смысл):** **Admin** → **«Открыть дашборд метрик»**, **«Сформировать отчёт (неделя/месяц)»**, **«Экспортировать CSV для анализа»**; опционально ассоциация к **Analytics store** как внутреннему классу (на схеме можно обозначить как подпись под системой, без отдельного актора).

**Main flow:** выбрать период → система собирает агрегаты из пайплайна событий → отображение в UI или отправка по расписанию (согласно `FR-AN-003`).

### UC-ManageIngredientMasterData

- **Цель:** вести справочник ингредиентов, синонимы, замены, связь с аллергенами и нутриентами на 100 г — основа корректного **FR-DE-002** и списков покупок.
- **Акторы:** Admin (или Content Ops; до выделения роли — **Admin**).
- **Связь:** `FR-RS-005`, пересечения с парсингом и обогащением.

**Диаграмма (UML, смысл):** **Admin** → **«Создать / изменить ингредиент»**, **«Слить дубликаты / синонимы»**, **«Проверить покрытие нутриентов»**; при сохранении критичных полей возможен последующий пересчёт КБЖУ затронутых рецептов (**FR-DE-002**) — на схеме пунктир от сценария к подписи «batch enrich» под системой.

**Main flow:** поиск конфликтующих названий → правка атрибутов → сохранение → триггер фонового перерасчёта затронутых рецептов по политике (батчами).
